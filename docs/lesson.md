# Занятие: как подготовить данные для RAG

Продолжительность: 80–90 минут. Предварительные знания: Python, виртуальные окружения, функции, списки и словари. Преподаватель заранее устанавливает зависимости и проверяет доступ к `/embeddings`, если планируется реальный режим.

## План

| Время | Демонстрация | Что должен понять студент |
|---|---|---|
| 0–10 мин | Задача поиска в правилах учебного центра | Зачем LLM внешний контекст; индексация и генерация — разные этапы |
| 10–20 мин | `Document`, загрузчики TXT/PDF, метаданные | Текст отделён от источника; PDF — список страниц |
| 20–35 мин | Сравнить chunk_size=250/500 и overlap=0/100 в notebook | Граница может разорвать факт; перекрытие даёт избыточность |
| 35–50 мин | Векторы и поиск: сначала demo, затем настоящий API | Близость векторов; слова против смысла; документ и запрос в одной модели |
| 50–65 мин | Chroma + SQLRecordManager, три индексации | Повтор, изменение, удаление; `full` против `incremental` |
| 65–75 мин | MultiVectorRetriever | Можно искать по одному представлению, возвращать другое |
| 75–90 мин | Упражнения и обсуждение RAPTOR/ColBERT | Качество и стоимость индексации; пределы одного вектора |

## Минимальный результат студента

Студент демонстрирует два поиска по своей коллекции, находит `source` результата, объясняет влияние chunk_size и показывает, что повторная индексация пропускает неизменившиеся чанки. Затем меняет один факт, удаляет файл и подтверждает, что старых версий больше нет.

## Практические задания

1. Добавьте TXT о спортивном центре. Выполните индексацию дважды. Объясните `num_added`, `num_skipped`, `num_deleted`, `num_updated`. Не требуйте роста именно `num_updated`: при изменении содержимого LangChain часто добавляет новый ID и удаляет старый.
2. Для вопроса «Какие выплаты положены учащимся?» сравните demo и реальную embedding-модель. Объясните, почему demo не годится для оценки семантики.
3. В notebook создайте две настройки splitter с разными размерами и перекрытием. Найдите случай, когда сумма и условие получения стипендии оказались в разных чанках. Укажите исходный файл и границы.
4. Сравните рекурсивное разбиение и `MarkdownHeaderTextSplitter`: какие метаданные добавляются, какие фрагменты сохраняют структуру разделов? В основном индексе используется только рекурсивное разбиение, чтобы не смешивать эксперименты.
5. Объясните, зачем `source` стабилен относительно папки `data`, а не абсолютного пути компьютера преподавателя.
6. В MultiVectorRetriever найдите `doc_id`: сколько коротких представлений можно связать с одним родителем? Измените пример, добавив ещё одно представление каждого родителя — например, список вопросов. Измерьте, сколько новых запросов эмбеддингов потребовалось.
7. Дополнительно: исследуйте PGVector из [примера i](https://github.com/langchain-ai/learning-langchain/blob/master/ch2/py/i-pg-vector.py). Перечислите изменения для замены локального Chroma на PostgreSQL и преимущества серверного хранилища для нескольких пользователей.

## Вопросы и ориентиры для преподавателя

**Почему не отправить всё в LLM?** Корпус растёт, контекст и бюджет ограничены. Индекс нужен, чтобы выбирать релевантные фрагменты.

**Почему нельзя индексировать одной моделью, а запрос другой?** Их координатные пространства могут не совпадать даже при одинаковой размерности.

**Что хранит SQLRecordManager?** Хеши, источники и сведения об обновлении, а не семантические векторы. Он позволяет пропускать неизменившиеся записи и удалять устаревшие через vectorstore.

**Почему выбран full?** Каждая команда получает весь снимок каталога, поэтому исчезнувшие источники тоже должны удаляться. Для потока отдельных обновлённых источников нужен incremental; удаление полностью исчезнувших источников требует отдельного учёта.

**Зачем overlap?** Сохранить контекст у границ; цена — больше текста, векторов и повторяющихся результатов. Рекурсивный splitter старается учитывать разделители, поэтому фактическое перекрытие не всегда точно равно заданному.

**Всегда ли наиболее близкий фрагмент отвечает на вопрос?** Нет. Top-k всегда возвращает ближайшее из доступного. Добавьте вопрос о стоимости парковки: в корпусе ответа нет. Проверка достаточности контекста и генерация — следующий этап.

## Продвинутые идеи из конца главы

**MultiVectorRetriever** уже реализован: краткие описания индексируются как дочерние документы, а `docstore` хранит полный текст. В этом проекте это временная демонстрация в памяти. В demo описания обрезаны, в реальном режиме генерируются ChatOpenAI. У одного родителя могут быть несколько векторов: резюме, вопросы, мелкие чанки.

**RAPTOR**: сгруппировать похожие фрагменты, получить резюме групп, повторять выше по дереву, индексировать оригиналы и резюме. Обсудите: какие вопросы требуют обобщения нескольких документов? Где суммаризация теряет числа или исключения? Здесь алгоритм не реализован, и обычный MultiVectorRetriever не называется RAPTOR.

**ColBERT**: вместо одного вектора на текст — контекстные векторы токенов, затем позднее взаимодействие (MaxSim: для каждого токена запроса взять наибольшее сходство с токенами документа и сложить значения). Это иной способ индексации и оценки, требующий отдельных моделей и инфраструктуры. Пример [l-rag-colbert.py](https://github.com/langchain-ai/learning-langchain/blob/master/ch2/py/l-rag-colbert.py) использует RAGatouille; установка не входит в окружение занятия. Обычный `/embeddings` провайдера не равнозначен ColBERT.
